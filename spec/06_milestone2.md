# Spec: Milestone 2 — горизонт как производное от due_date

> Старт milestone: сообщение пользователя "observations" (счётчики не обновляются,
> новая задача всегда в Сегодня, коробка не синхронизирована с due_date).
> Решение: горизонт ВЫЧИСЛЯЕМЫЙ из due_date, без хранения как независимого поля,
> без cron. Реализуется фильтрами запросов к БД.
> Эти правила дополняют/уточняют BR-1..BR-6.

## BR-7: Горизонт вычисляется из due_date (НЕ ручное поле)
Горизонт задачи (INBOX/TODAY/WEEK/LATER) — производное от `due_date` и текущего момента,
а НЕ выбираемое пользователем независимое поле. Правило (из APK `calculateTaskType`):
- `due_date` отсутствует → **INBOX**
- `due_date` ≤ конец сегодня (включая просроченные) → **TODAY**
- `due_date` ≤ конец текущей недели → **WEEK**
- `due_date` дальше → **LATER**
Границы дня/недели: `getTodaySOD`/`getTodayEOD`-эквиваленты в серверном времени пользователя.

## BR-8: Реализация на лету через запрос к БД (без cron)
Горизонт НЕ хранится как источник истины. Списки горизонтов строятся фильтром по `due_date`
прямо в запросе (с индексом по `due_date`), не загрузкой всех задач в память.
- Корректность в полночь — автоматическая: задача с датой "завтра" сама окажется в TODAY
  при первом запросе после полуночи, без фоновых процессов.
- Поле `task_type` в модели НЕ используется как независимый выбор. (Может остаться в схеме
  для совместимости/импорта, но не как источник горизонта. Если убираем — отметить миграцией.)

## BR-9: Новая задача без даты → INBOX
Дефолт формы создания НЕ TODAY. Новая задача без `due_date` попадает в INBOX (следствие BR-7).
ИСПРАВЛЯЕТ наблюдение "новая задача всегда приходит в Сегодня".

## BR-10: Изменение due_date синхронизирует горизонт немедленно
При создании/редактировании задачи и при любой смене `due_date` горизонт пересчитывается
сразу (следствие вычисляемости — пересчёт не нужен отдельно, т.к. горизонт = функция от даты).
ИСПРАВЛЯЕТ наблюдение "коробка не синхронизирована с due_date".
Если останется отдельное действие "переместить в горизонт" (move) — оно должно
менять `due_date` под целевой горизонт (например, "в TODAY" → due_date=сегодня), а не
task_type напрямую. Перемещение без даты в LATER/WEEK — задать соответствующую дату.

## BR-11: Счётчики меню всегда отражают текущее состояние
Счётчики горизонтов в сайдбаре пересчитываются при ЛЮБОМ изменении, влияющем на состав
(создание, удаление, завершение, смена due_date, move). HTMX-ответ таких действий должен
обновлять и блок счётчиков (out-of-band swap или общий перерендер сайдбара), а не только
список. ИСПРАВЛЯЕТ наблюдение "счётчики левого меню не обновляются".

## Флаг проекта (is_project) — ОСТАЁТСЯ в UI
- **`is_project` присутствует в форме/редакторе задачи** (переключатель "это проект").
  Задача легко конвертируется в проект и обратно, как было задумано в оригинале.
- Флаг сохраняется и доступен; полноценное поведение проекта-контейнера (отображение
  подзадач под ним) появится вместе с деревом в будущей вехе. До тех пор флаг хранится
  и помечает задачу, но визуального контейнера ещё нет.

## Out of scope для Milestone 2 (явно НЕ делать)
- **Подзадачи / иерархия** (`parent`/`childrenIds`): НЕ показывать в форме/редакторе задачи,
  не реализовывать дерево и разворачивание. Поле `parent` ОСТАЁТСЯ в модели (схему не ломать),
  но в UI редактирования задачи отсутствует. Дерево — отдельный будущий milestone.

## Следующий шаг (НЕ часть Milestone 2 — делать после него)

### Drag&drop переупорядочивание задач в списке
Подтверждено из APK: `ReorderRecyclerView` + `MenuAdapter.onMoveItem` (мобильная версия).
Десктопная версия в APK не представлена, но дробный `priority` — серверное поле, общее для
всех клиентов, что указывает на ручное переупорядочивание и в вебе.
- Поведение: перетаскивание меняет ТОЛЬКО `priority` (через `services.priority_between`),
  НЕ трогает горизонт — горизонт по-прежнему производное от due_date (BR-7). То есть тащить
  можно для порядка ВНУТРИ коробки.
- Инфраструктура уже есть: `priority` (дробный ранг), `services.priority_between/next_priority`
  (из APK `calcNewPriority/getMaxTaskPriority`). Не хватает UI + одной вьюхи.
- Реализация на вебе: библиотека перетаскивания (например SortableJS); на дропе вьюха
  принимает id задачи и id соседей (before/after), зовёт `priority_between` и сохраняет.
- ПОЧЕМУ отдельным шагом: зависит от стабильного списка/горизонтов из Milestone 2; делать
  только после того, как BR-7..BR-11 готовы и зелёные.

> **Статус — РЕАЛИЗОВАНО (2026-06-11):** `task_reorder` зовёт `services.priority_between`
> от соседей перетаскиваемой задачи; SortableJS в base.html (реинициализация на
> `htmx:afterSettle`), включён на плоском списке только при sort=priority и без группировки.
> Меняется ТОЛЬКО priority, горизонт остаётся производным от due_date.

## Отложенные шаги — повторяющиеся задачи (НЕ часть Milestone 2)

Порядок: сначала (A) материализация, потом (B) визуальная группировка — B зависит от A.

### A. Материализация повторов (из APK — базовое поведение)
Подтверждено структурой APK: повторы хранятся как СВЯЗАННЫЕ ЭКЗЕМПЛЯРЫ, не как одна
"умная" запись. Поля уже в модели: `recur_rule` (RRULE), `recur_parent_id` (связь серии),
`recur_exclude_dates` (EXDATE — пропущенные/удалённые вхождения).
- В оригинале разворачивание повторов было СЕРВЕРНЫМ (клиент `Manager._processServerTasks`
  только принимал готовые задачи; методов генерации на клиенте нет). В клоне эту роль берёт
  наш бэкенд.
- Поведение (ПРОЕКТНОЕ РЕШЕНИЕ, реконструкция — точный триггер в APK не виден):
  при завершении повторяющейся задачи создаётся следующий экземпляр со сдвинутым `due_date`
  по RRULE; экземпляры связаны через `recur_parent_id`; точечно удалённые/пропущенные даты
  пишутся в `recur_exclude_dates`.
- Привязка к дате: следующий `due_date` вычисляется по RRULE от предыдущего; горизонт нового
  экземпляра следует из `due_date` автоматически (BR-7) — отдельной логики коробки не нужно.
- Catch-up пропущенных дней: при отсутствии пользователя несколько дней образуется несколько
  просроченных экземпляров (каждый со своим `due_date` в прошлом → попадают в TODAY по BR-7).
  Для их появления нужен периодический пересчёт (здесь допустим cron/Celery-beat — в отличие
  от горизонтов; это материализация записей, а не вычисление вида).
- **Изменения БД: НЕ требуются** — все поля уже есть.

> **Статус A — РЕАЛИЗОВАНО (2026-06-11):** `services.spawn_next_occurrence` (на завершении,
> BR-5) + `services.materialize_due_recurrences` (catch-up) + management-команда
> `materialize_recurrences` (для cron). Следующая дата по RRULE через `python-dateutil`,
> пропуская EXDATE; генерация идемпотентна (не дублирует существующее вхождение). EXDATE
> пишется на корень серии при удалении вхождения (`services.exclude_occurrence`, вызывается
> из `task_delete`). Catch-up материализует только прошлые даты (≤ now), будущее вхождение
> появляется на завершении. Серия завершается по COUNT/UNTIL.

### B. Визуальная группировка просроченных повторов (ПРОЕКТНОЕ РЕШЕНИЕ, НЕ из APK)
Схлопывание пропущенных повторов в данных в APK НЕ обнаружено (нет поля-счётчика, нет метода
агрегации). Поэтому делаем как УЛУЧШЕНИЕ ПОВЕРХ оригинала — чисто визуальное, без изменения данных.
- Поведение: несколько просроченных экземпляров ОДНОЙ серии (общий `recur_parent_id`,
  `due_date` в прошлом, не выполнены) показываются в списке ОДНОЙ свёрнутой строкой со
  счётчиком (например "Полить цветы · ×3 просрочено") и кнопкой «отметить все».
- «Отметить все»: завершает все экземпляры группы разом (цикл `services.set_done`, BR-3).
  Опционально — можно разворачивать группу в отдельные строки.
- Счётчик: `COUNT` экземпляров группы, вычисляется запросом, НЕ хранится.
- Зависит от A: группировать нечего, пока экземпляры не материализуются (`recur_parent_id`
  заполняется в шаге A).
- **Изменения БД: НЕ требуются** — фича целиком в слое запросов/представления.
  Опирается на существующие `recur_parent_id`, `due_date`, `done`.

> **Статус B — РЕАЛИЗОВАНО (2026-06-11):** `views._collapse_recurrences` сворачивает
> ≥2 просроченных вхождения одной серии в строку "· ×N просрочено" (только в плоском
> списке); `recur_group_done` завершает всю группу через `services.set_done`. Чисто
> визуально, данные не меняются.
