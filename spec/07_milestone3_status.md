## Проектное решение: шаблоны целей — майлстоуны, не дельта-дни
Зафиксировано по итогам обсуждения (2026-06-11):
- **Майлстоуны** — основной и достаточный механизм структурирования шаблонов: этапы,
  внутри которых сгруппированы задачи, идущие последовательно ("серии операций").
- **Дельта-дни** (относительные смещения `*Days`: goalDueDateDays / dueDateDays /
  startDateDays / hiddenUntilDays) — РЕАЛИЗОВАНЫ и протестированы (BR-18), но признаны
  НЕ нужными в основном UX. Решение: код оставить (рабочий, не мешает), но НЕ выставлять
  смещения в UI создания шаблона/цели и НЕ развивать эту механику.
- Для Claude Code: дельта-дни НЕ считать недоделанными и НЕ "дотягивать". Это осознанно
  отключённая из UX фича, а не пробел. Если когда-нибудь понадобятся процессы со сроками —
  вернуться к ним отдельным решением.
- Зависимости-цепочки ("Б после А" с блокировкой) — НЕ реализуются: майлстоунов достаточно.
  В оригинальном MaxDone зависимостей задач тоже не было (только майлстоуны + относительные
  даты), так что это не пробел относительно оригинала.

## Поправка к Milestone 2 + баг-фиксы (2026-06-11)

### BR-20: Гибридная модель горизонта (ЗАМЕНЯЕТ часть BR-7/BR-9)
ОСОЗНАННЫЙ разворот прежнего "всё от даты":
- Задача С `due_to` → горизонт ВЫЧИСЛЯЕТСЯ из даты (BR-7 в силе для датированных).
- Задача БЕЗ `due_to` → остаётся в той коробке, где СОЗДАНА; коробка хранится как её
  значение (для бездатных task_type снова значимое поле, не только вычисление).
- Следствие (принято осознанно): бездатная задача не "переезжает" сама — остаётся в своей
  коробке, пока не выполнена или не перемещена вручную. INBOX — для задач, явно туда
  отправленных/созданных, а не дефолт для всех бездатных.
- ОТМЕНЯЕТ BR-9 (было: новая без даты → всегда INBOX). Теперь новая без даты → коробка,
  активная при создании.

### BR-21: Действие "в инбокс" (новая кнопка-иконка в редакторе)
Рядом с "дублировать / архив / удалить" добавить иконку **"в инбокс"**.
- Переводит задачу в INBOX И очищает `due_to` (due_to = null).
- Это штатный способ вернуть бездатную задачу во входящие и снять дату одним действием.
- HTMX-post, target #task-list, закрывает редактор (как соседние действия).

### BR-22: Просроченная дата — красная подсветка
Если `due_to` в прошлом (< сегодня) И задача не выполнена → дата подсвечивается красным
(акцент на просрочку; в оригинале также эмодзи 🔥 — опционально). Чисто визуально.

### BR-23: Подзадачи — toggle done по клику, НЕ удаление
БАГ: клик по подзадаче сейчас удаляет её. Должно: клик переключает `done` (как чекбокс),
с зачёркиванием выполненной. Удаление подзадачи — ОТДЕЛЬНОЕ явное действие (иконка/жест),
не основной клик. Касается дочерних задач дерева (`parent`/children); пункты чек-листа
(CheckListItem) уже работают корректно.

### BR-24: Установка повтора без даты → ближайшая дата по правилу
Повтор требует якорной даты (RRULE считается от due_to). Если пользователь ставит повтор
задаче БЕЗ `due_to`:
- система вычисляет БЛИЖАЙШУЮ дату, удовлетворяющую правилу, и ставит её в `due_to`.
  Примеры: "каждый вторник" → ближайший вторник; "каждый день" → сегодня.
- НЕ "сегодня вслепую" — именно первая дата по RRULE.
- После этого горизонт вычисляется из проставленной даты (BR-20 для датированных).

### BR-25: Повтор в инбоксе — "спит" без даты
Уточняет BR-21 ("в инбокс" очищает due_to) для повторяющихся задач:
- "В инбокс" у повторяющейся задачи → `due_to` очищается, НО `recur_rule` СОХРАНЯЕТСЯ.
  Повторяющаяся задача может лежать в INBOX без даты (повтор "спит").
- Запрета на "в инбокс" для повторяющихся НЕТ; повтор не теряется.
- При ВЫПОЛНЕНИИ бездатного повтора в инбоксе: следующий экземпляр датируется по правилу
  ОТ СЕГОДНЯ (точка отсчёта = момент выполнения, раз даты не было), затем по RRULE.
  Новый экземпляр получает `due_to` и автоматически уходит в свою коробку (BR-20/BR-7).
- Итог: INBOX работает как пауза для повтора — задача ждёт без даты, при выполнении
  оживает на следующую дату и переезжает в нужный горизонт.

### BR-30 / BR-31: Сохранение активной коробки (два бага, общая первопричина)
Первопричина обоих: активная коробка (горизонт) не отслеживается как состояние,
переживающее HTMX-обновления. Чинить системно, не порознь.

**BR-30: Удаление возвращает в ТЕКУЩУЮ коробку, не в TODAY.**
- Баг: после удаления задачи пользователь оказывается в списке TODAY.
- Причина: вьюхи действий берут горизонт как `request.GET.get("h", "TODAY")` —
  при отсутствии параметра дефолтят в TODAY.
- Фикс: все действия (delete, duplicate, archive, move, в инбокс) ДОЛЖНЫ получать и
  сохранять текущую активную коробку и возвращать список именно её.

**BR-31: Активный пункт меню следует за переключением.**
- Баг: подсветка активной коробки в сайдбаре определяется при ЗАГРУЗКЕ и не меняется
  при переключении коробок через HTMX.
- Причина: переключение подменяет только `#task-list`, сайдбар (класс nav-item-active)
  не обновляется.
- Фикс: активный пункт обновляется при переключении — через OOB-swap сайдбара
  (механизм OOB для счётчиков УЖЕ ЕСТЬ — расширить его, чтобы нёс и активное состояние)
  или общий перерендер с актуальным активным горизонтом.

Общее: ввести единый источник "текущая активная коробка", который (а) определяет подсветку,
(б) передаётся во все действия, (в) обновляется при переключении.

### BR-32: Drag&drop порядка в чек-листе и подзадачах (в редакторе задачи)
Переиспользует существующий механизм drag&drop (SortableJS + дробный priority), уже
работающий в основном списке. Два места в редакторе открытой задачи:
- **Чек-лист**: перетаскивание пунктов меняет `CheckListItem.sort_order` (поле уже есть).
- **Подзадачи** (дочерние задачи): перетаскивание меняет `priority` через
  `services.priority_between` В ПРЕДЕЛАХ детей одного родителя (тот же механизм, что
  task_reorder в списке, с фильтром по parent).
- **Доступно ВСЕГДА** (без условия sort=priority/group=none): в редакторе нет переключателей
  сортировки/группировки, поэтому условие активации не нужно — оно было бы мёртвым кодом.
  Самый простой и адекватный вариант.
- **Изменения БД: НЕ требуются** — `sort_order` и `priority` уже в модели.
- Реализация: SortableJS на двух списках в редакторе + эндпоинты reorder (можно переиспользовать/
  расширить существующий task_reorder для подзадач; для чек-листа — простой апдейт sort_order).

### BR-33: Редактирование задачи — черновик + буфер правок (подход А, за флагом)
ОБРАТИМАЯ фича: внедряется аддитивно за feature-флагом. Выключение флага → возврат к
текущей форме с кнопкой "Сохранить" (старый путь не удаляется).
- **Создание**: ввод названия → на blur создаётся черновик задачи. Пустой черновик без
  названия не сохраняется/удаляется.
- **Редактирование**: правки полей копятся в КЛИЕНТСКОМ буфере (Alpine), на сервер не идут
  до явного "Сохранить". "Отмена" — выбросить буфер, вернуть как было (откат в сессии).
- **Наименее инвазивно**: бэкенд НЕ меняется. "Сохранить" = существующий task_update одним
  запросом; "Отмена" = сброс клиентского состояния, запроса нет. Бизнес-правила (горизонт от
  даты, повторы) не затрагиваются — побочные эффекты только в момент явного сохранения.
- **Мобильный**: редактор полноэкранный (см. адаптив); системный "назад" при несохранённых
  правках → подтверждение "сохранить изменения?".
- **Откат фичи**: всё за флагом, старый код-путь сохранён → отключение возвращает форму.
- Задел на будущее (НЕ сейчас): серверная история правок может опереться на единый путь
  сохранения + существующие modified/local_change_date. Отдельный отложенный шаг.
