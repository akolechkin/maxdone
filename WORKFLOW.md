# WORKFLOW — spec-driven цикл для maxdone

Две дорожки правок. Обе заканчиваются зелёными тестами.

## Дорожка A — правлю СПЕКУ (основной путь)

Когда: меняется доменная модель, бизнес-правило или контракт.

1. Отредактируй нужный файл в `spec/`.
2. Промпт Claude Code, например:
   > Спека `spec/01_domain.md` изменена: у Task добавлено поле `pinned: Boolean default False`.
   > Регенерируй модель Task и создай миграцию строго по спеке. Не трогай вьюхи.
   > Затем обнови тесты по `spec/02_rules.md` если затронуто поведение, и прогони их.
3. Посмотри дифф регенерированного артефакта (`git diff tasks/models.py`).
4. `python manage.py test` — должно быть зелёным.
5. Коммит: `spec: add Task.pinned + regenerate model`.

## Дорожка B — правлю КОД по-быстрому

Когда: мелкая правка вьюхи/шаблона/рефактор без смены поведения.

1. Правишь код напрямую.
2. `python manage.py test` — ОБЯЗАТЕЛЬНО зелёное.
3. Если тест упал — ты изменил ПОВЕДЕНИЕ. Два варианта:
   - откатить (это была случайная регрессия), ИЛИ
   - это намеренно → иди в Дорожку A: обнови `spec/`, потом тест, потом код.
4. Коммит только при зелёных тестах.

## Правило против дрейфа
НИКОГДА не генерируй спеку из кода для «сверки». Спека пишется человеком и
ведёт код, не наоборот. Сверку обеспечивают ТЕСТЫ, а не обратная генерация.

## Регенерация "ядра с нуля" (сценарий сверки)
Для детерминированных артефактов (модели/миграции) можно попросить:
> Перегенерируй tasks/models.py с нуля строго из spec/01_domain.md во временный
> файл и покажи дифф с текущим. Не применяй, пока я не подтвержу.
Так ловится дрейф модели от спеки. Для вьюх/шаблонов так НЕ делать (разброс велик).
